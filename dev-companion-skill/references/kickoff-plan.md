# 开局规划（仅首次开工）

## 什么时候做

**两个条件同时满足才做**：

1. 用户要开工（不是纯问答，也不是解释）
2. `dev-tree/TREE.md` 不存在

已经有树 → **不做**，走常规流程。树里已经有顺序了，再排一份就是两份互相打架的计划。

## 与「没回答就别先动树」的关系

自检第 2 条写着「没回答就别先动树」。**开局规划是这条的唯一例外。**

理由：树需要一个起点，而这个起点不可能等到用户做出第一个决策才出现——在那之前树是空的，
能力 C 的「下一步」没有可定位的节点，H10 就作废了。

例外**仅限于此**：排完初始序列后**立即停下来问用户一次**（见下）。除此之外，
任何时候没有用户决策就不动树。

## 三档输入

| 档 | 来源 | 拿到之后 |
|---|---|---|
| 1 | 契约文件：`.project/requirements/` 的需求卡、`.project/design/tech/interfaces.yaml` | 先核对 `produced_by` 是本包 skill 名，核对不过就降回第 2 档 |
| 2 | 用户原始输入——对话里的描述、贴出的文件 | 正常排，不阻塞 |
| 3 | 提问 | 只在**排序有实质分歧**时问，≤ 3 题，每题带推荐值（H8） |

上游产物不存在时不阻塞、不报错——少了依据就在版本文档里写清少了什么。

## 排什么

产出**里程碑序列**，每个里程碑写清三件事：

1. **可验证的产物**——「links 表建好并能插入一条」，不是「完成 80%」
2. **依赖**——哪些里程碑必须在它之前
3. **落到哪些上游条目**——`REQ-xxx` / `IF-xxx`，对不上的记一条待确认

排序的判据按优先级：

- 技术依赖（数据层 → 接口 → 界面）优先于
- 风险（先做未验证的部分）优先于
- 用户价值（先做能独立交付的）

## 不做什么

- **不估工期、人手、上线时间。** 估算会变成承诺，而本 Skill 不产出这类信息。
  想要里程碑的规模，就写「这一期交付什么」，不写「要几天」。
- 不做技术选型——归 `tech-design-skill`
- 不改需求、不改接口契约——只读上游
- 不排超过 5 个里程碑——排太细会在第一轮就失效，剩下的等做进去再长节点

## 输出

写进 `TREE.md` 第一版与 `versions/001-*.md`：

- 顶层节点 = 里程碑序列（按依赖排序）
- 每个里程碑下挂它要落地的任务，任务是叶子
- 版本文档里写清依赖、每期的可验证产物、以及上游缺失的部分

严格遵守树的既有协议：待完成节点必须是叶子（H2）、写进版本文档而不是树里塞元信息（H7）。

## 必须问一次

排完把序列给用户看，问一句「这个顺序行不行」，**推荐值就是你排的这版**（H8）。

- 用户认可 → 进入常规的决策点流程
- 用户调整 → 按调整后重写，再确认一次
- 用户说「你自己看着办」→ 执行推荐值，并在版本文档里记一句「按推荐顺序开工，待用户确认」。
  **不要静默当成用户已确认**。

## 初始序列不是契约

用户确认后进入常规流程。后面要改顺序、拆分、合并，一律按 H2 / H11 走：
推翻已开工的节点加撤销记录并开新节点，不删历史。

开局规划只负责「第一次把顺序摆出来」，它不享有任何豁免。
