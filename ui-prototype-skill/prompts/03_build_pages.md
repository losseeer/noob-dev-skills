# 步骤 3：做页面

## 产物

默认写 `pages/index.html`，多页面时按页拆 `pages/<name>.html`。
`current.yaml` 的 `entry` 指向打开的第一个文件。

## 四条硬要求

1. **能直接打开。** 默认不依赖构建步骤、不依赖本地服务。数据可以 mock 在内存里，
   刷新即清空要在页面上或 `pages` 的 `note` 里写明。
2. **触发得到。** 步骤 1 抽出的每个 `error_case`，页面上都要有一条能走到它的输入路径。
   **把错误文案画在页面上不算**——得能真的触发出来。
3. **数值会变。** 涉及计数、列表增删、状态切换的，点了要真的变，哪怕是内存里的假数据。
4. **留白要写。** 没覆盖到的交互状态列进 `gaps`，或在页面底部写出来，不许默默略过。

## 内容上对齐什么

| 上游有什么 | 页面上要看到 |
|---|---|
| 接口的 `response` 字段 | 结果以可见的形式呈现（不是 console 里） |
| 接口的 `error_case` | 对应错误态可触发 |
| 需求卡的 `main_flow` | 主流程走得通 |
| 需求卡的 `acceptance_criteria` | 至少一条能在页面上被验证 |

## 边界

- **不写实现代码。** 不接真接口、不做生产级状态管理、不做鉴权。
  这是原型，目标是让人 review 交互，不是能上线。
- 不要写「已对接后端」这种话——数据是假的就直接说假的。

## 反模式

- 产出一个必须 `npm install` 才能看的东西，把 review 成本转嫁给用户。
- 页面看着像 UI 但点了没反应——那不是原型，是截图。
- 把 mock 数据写得像真实业务数据，让人误以为后端已经打通。
